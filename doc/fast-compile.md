# Fast compile

`solouvm check` 的目标：改完代码后，在几秒到几十秒内知道"能不能编过"，而不必等一次几分钟到几十分钟的完整编译与 elab（E 区需求）。

> 标注“待验证”的地方需要在真实工程和工具版本上确认。

## 1. 三层检查

```text
solouvm check
  1. slang 全量检查        所有分组            几秒～几十秒   语法、语义、类型、宏、include
  2. fake_top 编译         只编 tb 组          几十秒         厂商相关的语法与扩展、UVM 库兼容
  3. RTL 增量编译（P2）    rtl 改动文件及依赖   视改动量       vcs / xrun 的真实编译结果
```

从上到下依次执行，前一层有错误就停止，不再执行后面的层。各层可单独关闭（`--slang-only`、`--no-faketop`）。

`check` 不产生 run_id、不写 `runs/`、不碰回归的编译目录；生成物与产物都放在 `.solouvm/check/`。

## 2. 第一层：slang

### 2.1 调用方式

solouvm 调用 `slang` 可执行文件（E-01），不使用 pyslang：它是编译型扩展，无法以 vendor 方式内置（N-02）。

```text
slang -f .solouvm/check/check.f --lint-only --diag-json - [check.slang_args...]
```

`check.f` 由 `check` 生成，内容是合并的文件清单去掉 `check.exclude` 匹配的文件，加上全局与分组的 `+incdir+`、`+define+`，以及 UVM 源码（`check.uvm_src` 下的 `uvm_pkg.sv` 与对应的 `+incdir+`，E-11）。在 A 上运行时，其中的 `${VAR}` 由 solouvm 先用 A 的环境展开，再交给 slang。

待验证：

- `--lint-only` 与 `--diag-json` 等参数在所用 slang 版本中的确切名称与行为；没有 JSON 诊断输出时，退回解析文本诊断 `file:line:col: error: message`；
- UVM 库能否被 slang 完整解析，需实测各 UVM 版本；
- 只做 lint（不做完整 elab）时，未例化模块的参数相关错误能查到多少；
- 在 B 上运行时，slang 能否自己展开 `.f` 中的 `${VAR}`。

### 2.2 例外

slang 解析不了的内容必须能排除（E-03）：

| 情况 | 处理 |
|------|------|
| 加密 IP（`pragma protect`） | 加入 `check.exclude`；被排除文件中定义的模块，在其他文件中被例化时可能报"未知模块"，用 slang 的忽略未知模块选项消除 |
| 厂商私有系统任务（如 `$fsdbDumpvars`） | slang 默认会报未知系统任务，用对应的警告开关降级或关闭 |
| 厂商私有语法扩展 | 只能排除该文件；交给第二层的真实仿真器检查 |

通过 `check.slang_args` 追加 Slang 选项。`init` 生成的项目会设置 `["--timescale", "1ns/1ps"]`，为未声明时间单位的 UVM 库和设计单元提供默认值。使用 Slang 检查 UVM 工程时，将 `check.uvm_src` 指向含 `uvm_pkg.sv` 的 UVM 源码目录。

用 Verilator 运行 `init` 生成的 AXI 样例时，将兼容的 UVM 库目录以 `+incdir+` 加入 `FILES["tb"]`，并把库的 `uvm_pkg.sv` 放在工程的 UVM package 之前。使用无 DPI 的 UVM 库时，在 `defines` 加上 `UVM_NO_DPI`，并在 `builds.default.compile_opts` 加上 `["--timescale", "1ns/1ps"]`。可通过 `solouvm run --case smoke --seed 1` 固定种子运行。样例向 RTL 发出一笔地址事务，scoreboard 检查 monitor 采到的地址与长度。

### 2.3 运行位置

`check.where`（E-09）：

| 值 | 行为 |
|----|------|
| `auto`（默认） | A 上能找到 slang 就在 A 跑；否则经 provider 在 B 上跑 |
| `local` | 必须在 A 上跑 |
| `remote` | 必须在 B 上跑；会先 push |

在 A 上跑时，文件清单里位于项目根之外的路径（F-07）可能在 A 上不存在，此时自动改为在 B 上跑，并给出提示。

### 2.4 输出

诊断统一整理成（E-02）：

```text
rtl/axi_slv.sv:120:14: error: use of undeclared identifier 'addr_nxt'
tb/pkg/axi_env_pkg.sv:45:3: warning: unused variable 'cnt'

slang: 1 error, 1 warning in 3.2s (412 files)
```

`--format gcc` 输出与上面相同，便于 VS Code 等编辑器的 problem matcher 识别；`--format json` 输出结构化结果。

### 2.5 是否做增量

不做。slang 每次全量解析（Q4）。实现 E-01 ~ E-03 后，在实际工程上测量耗时并记录在本文附录；只有实测超过 30 秒时再重新评估。

## 3. 第二层：fake_top

### 3.1 为什么需要

slang 查的是语言层面的正确性，但真正跑回归的是 VCS / Xcelium / Questa，它们对某些语法有自己的理解或扩展。完整编译又要带上整个 RTL，很慢。fake_top 只编译验证环境，用真实仿真器在短时间内暴露 tb 侧的厂商相关错误（E-04）。

### 3.2 生成内容

`check` 扫描 `tb` 组文件，找出其中声明的 package，生成 `.solouvm/check/fake_top.sv`：

```systemverilog
// generated by solouvm -- do not edit
module solouvm_fake_top;
  import uvm_pkg::*;
  import axi_mst_pkg::*;
  import axi_env_pkg::*;
  import axi_test_pkg::*;
endmodule
```

- package 名称用正则 `^\s*package\s+(?:automatic\s+|static\s+)?(\w+)\s*;` 从 `tb` 组文件中提取，按文件清单中的顺序 import。
- 不例化 DUT，也不编译 `rtl` 与 `top` 组。
- **interface 是否需要例化：不确定。** virtual interface 在语言上只要求 interface 的声明被编译；但据我所知，至少 Questa 在找不到与 virtual interface 匹配的实例时会报错，参数化的 interface 更明显。实现时先用三个仿真器实测；不成立时的后备方案：fake_top 例化 `tb` 组中的每个 interface，输入端口接常量，参数取默认值，并对参数化 interface 按 tb 中实际用到的参数组合各例化一份。

### 3.3 编译命令

由后端的 `compile_only` 模板提供，例如：

| 后端 | 命令（示意） |
|------|--------------|
| VCS | `vcs -full64 -sverilog -ntb_opts uvm -f {filelist_tb} {fake_top} -top solouvm_fake_top -o {check_dir}/simv` |
| Xcelium | `xrun -64bit -sv -uvm -f {filelist_tb} {fake_top} -top solouvm_fake_top -elaborate -xmlibdirpath {check_dir}` |
| Questa | `vlog -sv -f {filelist_tb} {fake_top}` 后 `vopt solouvm_fake_top -o fake_opt` |

命令在 `.solouvm/check/` 中运行，文件清单中的路径相对于这个目录；产物也放在这里，与回归的编译目录分开，不互相影响。命令同样经 `run_job.sh`（`--kind check`）执行，享有超时与事实记录。上表命令为示意，不确定：各仿真器的最短命令序列需实测。

### 3.4 层次引用

tb 代码引用 DUT 层次路径（如 `tb_top.dut.u_core.state`）时，fake_top 中没有这些实例，编译必然失败。约定（Q5）：

- 层次引用与 `bind` 只能写在 `top` 组；
- fake_top 编译失败时，solouvm 检查错误信息是否属于"层次路径无法解析"一类；是的话提示（E-05）：

  ```text
  tb/pkg/axi_mon.sv:88: hierarchical reference 'tb_top.dut.u_core.state' cannot be resolved in fake_top.
  hint: move code that references the DUT hierarchy into the "top" file group (see doc/config.md §4.1)
  ```

各仿真器"层次路径无法解析"的错误码，实现时逐一收集。

## 4. 第三层：RTL 增量编译（P2）

只对 vcs / xrun 提供（Q4）。本节为方向性设计，实现前需要单独调研并补充。

### 4.1 改动检测

基线是"上次成功编译"，不是 git HEAD（E-07）。状态文件 `.solouvm/check/fast_state.json`，增量编译的产物也在 `.solouvm/check/` 下，不改动回归的编译目录：

```json
{
  "schema": 1,
  "options_hash": "…",
  "files": {
    "rtl/axi_slv.sv": {"mtime": 1762149302.1, "size": 18342, "sha1": "…"}
  }
}
```

- 先比较 mtime 与大小，有变化再算哈希，避免每次读全部文件；
- 编译选项（defines、incdirs、编译参数）的哈希变化时，直接全量编译；
- git 只作为加速提示：`git status --porcelain` 给出的文件优先检查。

### 4.2 依赖传播

改了下列内容时，依赖它的文件也要重编（E-08）：

| 改动 | 受影响的文件 |
|------|--------------|
| package | 所有 `import` 该 package 的文件 |
| `include` 的文件 | 所有 include 它的文件 |
| 宏定义所在文件 | 所有使用这些宏的文件——通常无法精确判断，退回全量 |
| 模块端口或参数 | 例化它的文件 |

依赖关系的来源：优先使用 slang 输出的依赖信息（待调研 slang 是否提供 depfile 或类似输出）；拿不到时用正则粗略扫描 `import`、`` `include ``。**任何无法确定的情况都退回全量编译**，宁慢勿错。

### 4.3 与仿真器增量机制的关系

VCS（三步流 `vlogan` + `vcs`）和 Xcelium 都有自己的增量编译。solouvm 的职责是算出"哪些文件该重编"并调用对应命令，不重新实现增量编译本身。具体命令序列在调研后补充。
