## D1 配置只用 Python

**决定**：项目配置、文件清单、case 定义都是 Python 模块，不解析 YAML / JSON / TOML 配置。

**理由**：验证工程师需要循环、条件、函数来批量生成 case 与参数；声明式格式最终都会长出半套模板语言。Python 本身就是最好的"配置语言 + 模板语言"。

**代价**：配置文件可以执行任意代码，加载即运行；不懂 Python 的人上手略难。

**备选**：YAML + Jinja（dvsim 风格的 hjson）——表达力弱且调试困难，放弃。

## D2 A 端零第三方依赖

**决定**：solouvm 运行时只用 Python 标准库，Python >= 3.10。

**理由**：EDA 服务器常常不能联网、不能随意 pip install；零依赖时把仓库拷过去即可使用。

**代价**：ssh 只能调用系统 `ssh` 命令；HTML 报告、表格输出要自己写。

## D3 生成 Makefile，生成物可以独立使用

**决定**：执行逻辑全部生成为 Makefile 与 shell 脚本，脱离 solouvm 也能 `make` 运行。

**理由**：团队已有的调度系统、CI 可以直接调用；solouvm 出问题时，用户仍能手动跑；生成物本身就是可读的"执行说明书"。

**代价**：执行逻辑受 make 与 shell 的表达力限制，复杂逻辑（retry、判定）只能放到 A 端。

## D4 执行机上不装 solouvm、不需要 Python

**决定**：B 上只需要 `make`、`bash`、POSIX 工具与仿真器。

**理由**：远程开发时 B 往往是共享的仿真服务器或集群节点，装软件需要走流程；不装任何东西，部署成本为零，也不存在 A、B 版本不一致的问题。

**代价**：B 上的一切行为都必须事先生成；超时、进程组管理等要用 shell 实现，并在 Linux 与 macOS 上分别验证（Q-02）。

**备选**：B 上运行 Python 版 `_exec`（旧设计）——要求 B 有合适版本的 Python 且能拿到 solouvm，放弃。

## D5 B 只记录事实，判定全部在 A

**决定**：`run_job.sh` 只写退出码、信号、超时等事实；pass / fail 由 A 读取事实与日志后判定。

**理由**：

- 判定规则改了不用重跑仿真，在 A 上重新 `judge` 即可；
- 判定逻辑只有一份，用 Python 写，可测试；
- B 上没有 Python，本来也无法做复杂判定。

**代价**：A 必须能读到 B 上的日志；远程场景下判定需要流式读取远端日志，耗时与日志大小相关。

**备选**：B 上用 shell 做简单判定——规则一复杂就难以维护，且与 A 的规则可能不一致，放弃。

## D6 事实文件用 `key=value` 文本

**决定**：`job.facts` 为 `key=value` 纯文本，开始时写一段、结束时追加一段。

**理由**：shell 用 `printf` 即可写，无需 JSON 转义；"只有开始段"天然表示中途死亡，不需要另写 pending 文件。

**代价**：只能表达扁平结构；值中不能有换行。

**备选**：JSON——shell 写 JSON 需要处理转义，且无法追加，放弃。

## D7 provider 拆成 transport / launcher / sync

**决定**：需求里的 provider 在实现上是三个独立接口的组合：transport（怎么在 B 上执行命令、读文件）、launcher（job 交给谁调度）、sync（文件怎么到 B）。

**理由**：三者正交。"ssh 到提交节点再 bsub"就是 ssh + lsf；"共享盘"就是 sync=none。不拆的话，每种组合都要单独实现一个 provider。

**代价**：用户配置多一层结构；为此提供了简写与 `local` 默认值。

## D8 调度器通过 Makefile 的 `SUBMIT` 变量接入

**决定**：每个编译与 job 命令前都有 `$(SUBMIT)`；直接 make 时为空，LSF 时为 `bsub -K ...`。

**理由**：Makefile 只有一份，手动执行与集群执行走同一套规则（D3）；新增调度器只需要给出 `SUBMIT` 的值。

**代价**：调度器必须支持"提交并阻塞等待"模式（LSF 的 `-K`、SGE 的 `-sync y`、Slurm 的 `srun`）。

## D9 超时实现依次回退

**决定**：`run_job.sh` 依次尝试 GNU `timeout`、`gtimeout`、内置 bash 实现（`set -m` + 看门狗）。

**理由**：Linux 自带 `timeout`；macOS 装了 coreutils 有 `gtimeout`；什么都没装的 macOS 也必须能用。

**代价**：三种实现的行为必须一致，需要在两个平台上都测试；内置实现的精度与边界情况需要格外小心。

## D10 retry 由 A 驱动，默认只重试环境失败

**决定**：失败 job 的重试由 A 在判定后生成子集再派发；`regress.retry_on` 默认只含 `error`。

**理由**：B 上没有判定能力，无法决定是否重试。设计失败重跑通常还是失败，默认重试只会延长回归时间；license 等环境失败重试大概率能过。

**代价**：重试有一轮"判定 → 再派发"的往返延迟。

## D11 共享生成物与每轮生成物分离

**决定**：`gen/` 放与具体轮次无关的生成物；`runs/<run_id>/` 放本轮的 `run.mk` 与结果；每次尝试在 `<job_id>/try<N>/`。

**理由**：两轮回归同时进行时互不覆盖（N-14）；首轮与重试的目录结构一致，判定代码不需要特殊处理。

**代价**：日志路径多了两层。

## D12 文件分 rtl / tb / top 三组

**决定**：DUT 层次引用与 `bind` 只能放在 `top` 组；fake_top 只编译 `tb` 组。

**理由**：完全禁止层次引用不现实；把它们限定在一个组里，fake_top 就一定能编过，且出错时能给出明确提示。

**代价**：用户需要按约定组织文件；只写平铺列表时无法使用 fake_top。

## D13 case 即文档：记录写在 Python 里

**决定**：case 的说明、负责人、开发阶段、bug、todo、调试记录都写在 `Case(...)` 里；markdown 只是导出物。

**理由**：不用另外维护文档和 bug 表，记录随代码进 git、随分支走；加载时可以校验；与回归结果天然关联。

**代价**：非验证人员（如设计）不方便直接编辑；记录多了 case 文件会变长（用一个 case 一个文件缓解）。

**备选**：每个 case 一个 markdown 文件——要解析 markdown 结构，与 D1 冲突，放弃。

## D14 bug 使用显式整数 ID

**决定**：`Bug(id=3, ...)` 必填，完整 ID 为 `burst#3`。

**理由**：显式编号绝对稳定，插入、删除其他记录都不变；短，便于口头和提交信息中引用。

**代价**：需要手动选编号；提供 `notes --next-id` 缓解。

**备选**：按声明顺序编号（插入即变）、"日期 + 序号"（同一天插入仍会变），放弃。

## D15 命令行输出用英文

**决定**：命令行输出、错误信息、日志一律英文；导出文档语言可配置，默认中文。

**理由**：英文输出便于 grep、贴到 issue、与仿真器的英文日志一起阅读，也避免终端编码问题。

## D16 选择结果为空时退出码为 2

**决定**：`--case` / `--tag` 等选不到任何 job 时报错退出；`--allow-empty` 可改为 0。

**理由**：CI 中 tag 拼错时，若返回 0，一次什么都没跑的回归会显示为通过，这是最危险的静默失败。

## D17 运行历史放在项目内

**决定**：`.solouvm/runs/<run_id>/`，整个 `.solouvm/` 加入 `.gitignore`，由保留策略控制体积。

**理由**：历史跟着项目与分支走，多个工作副本互不干扰，删项目即清理。

**代价**：项目目录体积会增长。

## D18 回归默认阻塞，可 detach

**决定**：`regress` 默认等待结束并显示进度，结束后自动判定；`--detach` 启动后立即返回。Ctrl-C 终止 B 上全部 job，对已完成的部分照常判定。

**理由**：交互使用最常见的诉求是"跑完给我结果"；夜间回归与 CI 用 detach。

## D19 slang 始终全量

**决定**：slang 检查不做增量；增量编译只针对 vcs / xrun，且为 P2。

**理由**：slang 解析很快，增量带来的依赖分析复杂度远大于收益；真正慢的是商用仿真器。

**代价**：超大工程上 slang 也可能变慢；以实测数据为准再评估（fast-compile.md §2.5）。

## D20 配置文件名为 `solouvm.conf.py`

**决定**：不使用 `solouvm.py`，检测到即报错。

**理由**：`solouvm.py` 会遮蔽 solouvm 库本身，`import solouvm` 会静默导入用户配置。

## D21 waiver 必须写理由，且只作用于被匹配的行

**决定**：`Waiver` 的 `reason` 必填；只扣除被匹配行的计数；可设上限与失效日期；报告列出已用、未用、过期的 waiver。

**理由**：避免为一条已知告警放宽整体上限；强制写理由与失效日期，防止 waiver 只增不减。

## D22 假仿真器用 bash 实现

**决定**：自测与示例用的 `fake` 后端是 bash 脚本。

**理由**：只有这样才能在测试中真实验证 D4（B 上不需要 Python）。

## D23 编译锁用 `mkdir`，残留锁按持有者存活情况清理

**背景**：同一个 build mode 被两轮回归同时编译时需要串行化；B 崩溃后锁可能残留。

**决定**：

- 获取锁：`mkdir build/<mode>.lock`，成功后写入 `owner` 文件，内容为 `<host> <pid> <run_id>`；
- 获取失败时读取 `owner`：同一主机且 PID 已不存在，视为残留，删除后重试；不同主机时等待，超过编译超时仍未释放则报错，提示 `solouvm clean --locks`；
- 释放：`run_job.sh` 退出时（包括被信号终止）删除锁目录。

**理由**：`mkdir` 在 Linux 与 macOS 上都是原子操作，不依赖 `flock`（macOS 默认没有）。

**代价**：跨主机的残留锁无法自动判断，需要人工清理。

## D24 job 命令直接写在 Makefile 中

**背景**：job 数上万时 Makefile 会很大。

**决定**：首版每个 job 一个目标，命令内联在 `run.mk` 中。

**理由**：一个目标约 500 字节，一万个 job 约 5 MB，GNU make 解析这种规模的 Makefile 在秒级；内联的 Makefile 自包含、可读，手动执行最方便。

**代价**：超大规模时可能变慢。若实测超过 2 万个 job 时解析超过 5 秒，改为每个 job 生成一个参数文件、Makefile 只引用路径。

## D25 LSF 使用 `bsub -K`，由 `make -j` 控制并发

**背景**：`-K` 让 bsub 阻塞到 job 结束，每个运行中的 job 在提交节点上占一个 bsub 进程。

**决定**：首版采用 `bsub -K`，并发上限即 `make -j` 的值。

**理由**：与 D8 一致，不需要额外的提交与轮询逻辑；bsub 进程很轻，几百个同时存在在提交节点上可以接受。

**代价**：并发上千时提交节点的进程数与 LSF 调度器压力较大。届时增加"批量提交 + 轮询"模式作为 launcher 的另一种实现（P3）。

## D26 `check` 发现代码错误时退出码为 1

**决定**：`check` 发现语法或编译错误时退出码 1；slang 或仿真器本身无法运行时退出码 2。

**理由**：`check` 的目的就是找代码错误，"找到了"是一种检查结果，与"测试失败"同类；2 保留给"无法完成检查"。这与 `build` 不同：`build` 是回归的前提，编不过意味着后续无法判定，所以是 2。

**代价**：同样是编译错误，`check` 与 `build` 的退出码不同，需要在文档中说明。
